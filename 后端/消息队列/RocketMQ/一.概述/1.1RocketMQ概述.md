# 一.概述

## 1.1MQ概述

---

- `MQ/Message Queue`:
	- 提供<mark style="background: #BBFABBA6;">消息队列服务</mark>的<mark style="background: #FFF3A3A6;">中间件</mark>，提供了一套消息<mark style="background: #FFF3A3A6;">生产，存储，消费</mark>的全过程<mark style="background: #ABF7F7A6;">`API`</mark>的软件系统
- 消息队列：
	- 存储和接收两端的中间层，两者不会相见
	- 实现类生产者和消费者的异步 ——》 解耦，无需阻塞等待，变为队列堆积
	- 优点：
		- 解耦：
			- 生产者，消费者通过中间件来交互，无需见到对方，<mark style="background: #ADCCFFA6;">无需和对方适配</mark>
		- 异步：
			- 中间件使生产者发完消息就走无需等待
		- 均衡：
		  ![[Excalidraw/后端/消息队列/RocketMQ/一.概述/一.概述/1.1MQ概述/限流削峰|限流削峰]]
			- 保证峰值时的信息可以累计，等到低谷期慢慢处理
		- 持久化：
			- 保存消息
		- 数据采集：
			- 分布式系统中会产生海量数据，使用`RocketMQ`是很好的选择

## 1.2常见的MQ

---

- `ActiveMQ`:
	- 很少使用了，底层为`java`
- `RabbitMQ`:
	- 不是`java`底层，需要二次开发适配项目，开发难度大
- `Kafka`:
	- 吞吐量极大，常用于大数据领域的实时计算，日志采集等场景，底层使用`java/scala`
	- 交互协议：没有使用常见的`MQ`协议，使用的是自研协议
- `RocketMQ`:
	- 阿里开发的基于`java`的`MQ`产品
	- 交互协议:自研协议
	- 配合:`springcloud alibaba`

## 1.3常见的协议

---

- `JMS`:
	- `java Messaging Service`，是`java平台`上有关`Message oriented middeware/mom`面向消息的中间件 的 <mark style="background: #FFB86CA6;">接口规范</mark>，类似`jdbc`，规范中间件的实现，<mark style="background: #BBFABBA6;">高级语言直接通过接口调用功能</mark>
- `STOMP`:
	- `streaming text orientated message potocol`,面向文本流的消息协议,提供可互连接
- `AMQP`:
	- 高级协议，应用层协议 通过<mark style="background: #FF5582A6;">`api调用提供服务`</mark>,兼容所有中间件和语言
	- `rabbitMQ实现就是靠这个`
- `MQTT:`
	- 消息队列遥测协议，常用于物联网中
	- `rabbitmq可以通过插件支持`

# 二.基础

## 2.1基础概念

---

- 消息`/message`:
	- 本质上就是数据
	- 传递数据需要对<mark style="background: #ABF7F7A6;">数据进行封装</mark> ——》 消息，消息到达`MQ`以后被实例化为一个实例
	- 消息在`kafka和rocket`中必须<mark style="background: #ABF7F7A6;">归属</mark>一个<mark style="background: #FFF3A3A6;">主题</mark>
- 主题/`topic`:
  ![[图片/Pasted image 20261029230953.png]]
	- 表示一类消息，<mark style="background: #ADCCFFA6;">对消息进行分类</mark>，一个消息只能是一种主题下面的消息
	- 一个主题可以包括多个消息
	- 一个<mark style="background: #D2B3FFA6;">生产者能生产多种的消息</mark>，但是<mark style="background: #FFB86CA6;">消费者只能订阅一种消息</mark>
- 标签/`tag`：
	- 主题下的标签，相当于小主题但是不用单独分出来一个主题，订阅时可以指定主题下的什么标签 ——》 实现主题内分类
	- 不同的主题可以使用相同的标签
	- 标签打在具体消息上面
- 队列/`queue`:
	- <mark style="background: #BBFABBA6;">消息存储的物理实体</mark>，一个`topic`中可以有多个`queue`，一个`topic中的queue`也被称为一个`topic`中消息的<mark style="background: #FF5582A6;">分区/`partition`</mark>
	- <mark style="background: #FFF3A3A6;">同一个消费组中</mark>，<mark style="background: #BBFABBA6;">同一时刻</mark>一个分区只能被一个消费者消费 ——》 <mark style="background: #ABF7F7A6;">防止同一个组内重复消费</mark>，但是同一时刻，<mark style="background: #D2B3FFA6;">消费者可以消费多个分区</mark>，但是不同消费者组间可以同时消费一个队列，因为各自消费组内部主机维护`offset`记录消费的位置
	  ![[图片/Pasted image 20261029233626.png]]
	- 队列中的`tag`不会产生任何影响
- 消息标识/`messageid /key`:
	- `Recket`中每个消息都有唯一标识的`MessageId`,且可以携带业务标识`key`，以方便对消息的查询
	- `MessageId`:
		- 生产者发送消息时`send()`产生一个`messageid`标识
			- 构成：
				- **客户端 IP、进程 PID、类加载器 hashcode、时间戳和自增序号**
			- 重发不变性：
				- 根据构成规则生成以后，若是重发也不会重新生成，继续使用之前的
		- 发送到`btoker`时也会差生一个`messageid`标识 ——》 `offsetMessageid`
			- 构成：
				- `brokerip + port + 物理分区的offset`
			- 重新接收发生变化：
				- 若是收到重复`messageid`的消息会改变`id` ——》 因为这个id是持久化消息以后进行物理地址分配的结果
			- 可以通过这个`id`<mark style="background: #ABF7F7A6;">直接定位</mark>获得消息
	- `key`:
		- 使用业务层的`id`，这是<mark style="background: #BBFABBA6;">业务层的唯一标识</mark>，<mark style="background: #FFB8EBA6;">尽可能唯一</mark>，若是不唯一使用模糊查询可能只能返回最近64条记录
		- 自己主动设置
		- 实例：
			- 订单号

## 2.2系统架构图

---

- 大体架构：
  ![[图片/Pasted image 20261031193619.png]]
	- `producer`:
		- 生产者：生产消息，通过`Mq`的负载均衡模块<mark style="background: #ADCCFFA6;">选择`Broker`集群的一个队列</mark>进行投递消息
		- 去`name server`中获得`broker`居群的信息，然后选择一个投递
		- 投递快速失败且低延迟：
			- 内部对于失败的`broket`会进行更改重试
		- 生产者组：
			- 同一类生产者的集合，发送相同`topic`类型的消息
			- 虽然发送相同的`topic`类型的消息，但是也<mark style="background: #FF5582A6;">能发送其他类型的</mark>消息，<mark style="background: #BBFABBA6;">只是不生产</mark>
		- 集群:
			- 本身就是一个集群
	- `consummer`:
	  ![[图片/Pasted image 20261031141651.png]]
		- 从`Broker`中读取消息，并且针对消息进行相关处理的过程 ——》 消费
		- 消费者组：
			- 同一类消费者的集合，只能消费一种`topic`消息 ——》 <mark style="background: #BBFABBA6;">负载均衡和容错</mark>目标实现
			- 消费者不能超过同一个`topic`队列的数量，若是超过了，代表一个`queue`要对应多个消费者，<mark style="background: #FFF3A3A6;">一个队列同一时刻</mark>同一个消费组<mark style="background: #BBFABBA6;">，只能被一个消费者消费</mark> ——》 多的消费者空闲
			- 消费者集合内部有一个机制进行协调均衡
	- `Name Server`:
		- `broker和topic的注册中心`:
			- 获得`broker`信息以后，组成一个信息表，消费者可以通过其可以知道`topic`在哪个`broker`中，同时记录了一个`topic`中不同队伍的分布
		- `Broker的管理者`,`broker`会主动通信告知自己的状态信息
		- 可以集群搭建，，但是这个集群不是主从关系，是无状态的，因为`broker`会向所有的`name server`中发送消息
	- `Broker`:
		- 消息的存储承载着
		- 可以组成一个集群，提高可靠性
			- 主从关系
				- 通过`broker id`区分主从，可以有多个从节点
				- 通过`broker name`区分主从节点的分组
			- 关系维护:
				- `producer与nameserver`中一个接待你建立长连接，定期从`nameserver`中获得映射表，通过映射表知道该向哪个`master`建立长连接，定期发送心跳包
				- `consumer和nameserver`的随机一个建立连接，获得映射表，并像提供服务的`master,slave`建立连接，定期发送心跳包

## 3.3Broker集群搭建

---

- 搭建流程:
	- 优先建立`nameserver`最先建立监听连接
	- 启动`broker`跟所有的`nameserver建立长连接`
	- 收发消息前先建立`topic`,并且指定改`topic`要存储在那些`broker`上，也可以在发送消息自动创建`topic`
	- `producer`先和`namerserver`先建立一个连接，获得映射表，在和对应的`master`建立连接
	- `consumer类似`

- 映射配置:
	- `host文件的编写`:
		- `/etc/hosts`
		- 主从`broker`要放到不同的主机上防止一台主机坏了，所有的都坏了
		- 可以在配置中直接使用主机映射 ——》 清晰易懂
	- 配置环境变量:
		- `/etc/profile`
	- 立即启动配置:
		- `source /etc/profile`
	- 创建消息存储路径:
		- `/data/rocketmq/store`
			- `commitlog`
			- `consumequeue`
			- `index`
	- `broker配置文件`:
		- 解压包中已经提供了一些实例文件，直接修改使用即可
		- `.../conf/2m-2s`:4个配置文件，双主双从配置信息
		- 参数:
			- `brokerClusterName`:
				- 同一个集群的名字相同
			- `brokername`:
				- 主从名字
			- `brokerid`:
				- 是主，是从
					- `1`:从
					- `0`:主
			- `deleteWhen`:
				- 不常用信息的删除时间
			- `brokerRole`:
				- 同步还是异步
			- `flushDiskType`:
				- 刷盘是异步还是同步
			- ....
			- 参数中的ip等信息可以使用`hosts`中的配置

```properties
# ======================================================
# 1. 集群与节点身份配置 (核心)
# ======================================================
# 集群名称，同一个集群内的所有节点必须保持一致
brokerClusterName=DefaultCluster
# Broker 名称：Master1 和它的 Slave1 必须叫同名，这里叫 broker-a
brokerName=broker-a
# Broker ID：0 代表 Master 节点，大于 0 代表 Slave 节点
brokerId=0
# Broker 角色：异步复制 Master（性能好），如果要强一致同步复制填 SYNC_MASTER
brokerRole=ASYNC_MASTER
# 刷盘方式：异步刷盘（性能好），如果对数据极其严格可填 SYNC_FLUSH
flushDiskType=ASYNC_FLUSH

# ======================================================
# 2. 网络与注册中心配置 (核心)
# ======================================================
# NameServer 地址，多个用分号 ; 隔开 (填两台机器的IP)
namesrvAddr=192.168.179.100:9876;192.168.179.101:9876
# 必须指定本机 IP，否则 Broker 会去获取虚拟网卡IP，导致生产/消费者连不上
brokerIP1=192.168.179.100
# 监听端口，默认 10911。同机部署多个 Broker 时，端口必须不同！
listenPort=10911

# ======================================================
# 3. 存储路径配置 (避坑重点：绝对不能用同一个目录)
# ======================================================
# 数据存储根目录 (这里指向你提前建好的目录)
storePathRootDir=/data/rocketmq/store-a-master
# CommitLog 存储目录（默认在根目录下，明确写出更清晰）
storePathCommitLog=/data/rocketmq/store-a-master/commitlog

# ======================================================
# 4. 磁盘与清理策略
# ======================================================
# 磁盘使用率超过 75% 触发只读保护 (建议别改太高，防止物理机被打爆)
diskMaxUsedSpaceRatio=75
# 凌晨 4 点清理过期文件
deleteWhen=04
# 消息文件保留时间（小时），默认 72 小时（3天）
fileReservedTime=72

# ======================================================
# 5. 业务特性
# ======================================================
# 是否允许自动创建 Topic（测试环境建议 true，生产环境建议 false 防止滥用）
autoCreateTopicEnable=true
# 是否允许自动创建订阅组
autoCreateSubscriptionGroup=true
```
