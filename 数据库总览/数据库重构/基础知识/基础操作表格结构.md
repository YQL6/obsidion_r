这套 `atguigudb` 可以理解为一个“跨国公司的组织、岗位与员工人事模型”。文件中共有 **9 张表、1 个视图**：`regions`、`countries`、`locations`、`departments`、`jobs`、`employees`、`job_history`、`job_grades`、`order` 和 `emp_details_view`。

## 一、表间关系

最核心的业务链路是：

```
地区 → 国家 → 办公地点 → 部门 → 员工 ← 岗位
```

完整关系如下：

```
regions
  │ 1:N
countries
  │ 1:N
locations
  │ 1:N
departments ─────1:N────> employees <────N:1──── jobs
  │                          │
  │                          └── manager_id 自关联到 employees.employee_id
  │
  └────1:N────> job_history <────N:1──── employees / jobs

job_grades ──按 salary 范围逻辑匹配──> employees.salary
order      独立表，与其他表没有外键关系
```

### 外键关系明细

|父表|子表|连接字段|关系含义|
|---|---|---|---|
|`regions`|`countries`|`region_id`|一个地区包含多个国家|
|`countries`|`locations`|`country_id`|一个国家有多个办公地点|
|`locations`|`departments`|`location_id`|一个办公地点可以设置多个部门|
|`departments`|`employees`|`department_id`|一个部门有多名员工|
|`jobs`|`employees`|`job_id`|一个岗位可以由多名员工担任|
|`employees`|`employees`|`manager_id → employee_id`|员工自关联，表示直属上级|
|`employees`|`job_history`|`employee_id`|一个员工可以有多条任职历史|
|`jobs`|`job_history`|`job_id`|历史记录中的岗位|
|`departments`|`job_history`|`department_id`|历史记录中的部门|
|`employees`|`departments`|`employee_id ← manager_id`|员工可以被指定为部门负责人|

需要注意：`departments` 和 `employees` 是相互引用的循环关系：

- `departments.manager_id` 指向 `employees.employee_id`
- `employees.department_id` 指向 `departments.department_id`

数据库只保证“负责人是已有员工”，但**不保证该负责人一定属于这个部门**。

## 三、列名含义

### 1. `regions`：地区表

|列名|中文含义|说明|
|---|---|---|
|`region_id`|地区编号|主键，例如 1、2、3|
|`region_name`|地区名称|如 Europe、Americas、Asia|

### 2. `countries`：国家表

|列名|中文含义|说明|
|---|---|---|
|`country_id`|国家代码|主键，两位字符，如 CN、US、JP|
|`country_name`|国家名称|如 China、United States|
|`region_id`|所属地区编号|外键，指向 `regions.region_id`|

### 3. `locations`：办公地点表

|列名|中文含义|说明|
|---|---|---|
|`location_id`|办公地点编号|主键|
|`street_address`|街道地址|详细地址|
|`postal_code`|邮政编码|使用字符串保存，避免丢失前导零|
|`city`|城市|如 Tokyo、London|
|`state_province`|州或省|如 Texas、Ontario|
|`country_id`|国家代码|外键，指向 `countries.country_id`|

### 4. `departments`：部门表

|列名|中文含义|说明|
|---|---|---|
|`department_id`|部门编号|主键|
|`department_name`|部门名称|如 IT、Finance、Sales|
|`manager_id`|部门负责人编号|外键，指向 `employees.employee_id`|
|`location_id`|部门办公地点编号|外键，指向 `locations.location_id`|

### 5. `jobs`：岗位表

|列名|中文含义|说明|
|---|---|---|
|`job_id`|岗位代码|主键，如 IT_PROG、SA_MAN|
|`job_title`|岗位名称|如 Programmer、Sales Manager|
|`min_salary`|岗位最低工资|该岗位的建议最低薪资|
|`max_salary`|岗位最高工资|该岗位的建议最高薪资|

`min_salary` 和 `max_salary` 描述的是“岗位的薪资范围”，不是某位员工的实际工资。

### 6. `employees`：员工表

|列名|中文含义|说明|
|---|---|---|
|`employee_id`|员工编号|主键|
|`first_name`|名|员工名字|
|`last_name`|姓|员工姓氏|
|`email`|电子邮箱|唯一，不能重复|
|`phone_number`|电话号码|使用字符串保存|
|`hire_date`|入职日期|员工进入公司的日期|
|`job_id`|当前岗位代码|外键，指向 `jobs.job_id`|
|`salary`|当前工资|两位小数，如 9000.00|
|`commission_pct`|佣金比例|0.20 通常表示 20%，没有佣金时为 NULL|
|`manager_id`|直属上级员工编号|自关联到 `employees.employee_id`|
|`department_id`|当前部门编号|外键，指向 `departments.department_id`|

这里有两个“经理”字段需要区分：

- `employees.manager_id`：该员工的直属上级。
- `departments.manager_id`：该部门的负责人。

它们含义不同，不是同一个字段。

### 7. `job_history`：任职历史表

|列名|中文含义|说明|
|---|---|---|
|`employee_id`|员工编号|外键，指向 `employees.employee_id`|
|`start_date`|任职开始日期|与员工编号共同组成主键|
|`end_date`|任职结束日期|不能为空|
|`job_id`|当时的岗位代码|外键，指向 `jobs.job_id`|
|`department_id`|当时所在部门编号|外键，指向 `departments.department_id`|

主键是 `(employee_id, start_date)`，表示同一员工在同一个开始日期只能有一条任职记录。

### 8. `job_grades`：薪资等级表

|列名|中文含义|说明|
|---|---|---|
|`grade_level`|薪资等级|如 A、B、C、D、E、F|
|`lowest_sal`|该等级最低工资|范围下限|
|`highest_sal`|该等级最高工资|范围上限|

该表没有 `job_id`，也没有被外键关联。它通常通过下面的逻辑与员工工资匹配：

```
employees.salary BETWEEN job_grades.lowest_sal AND job_grades.highest_sal
```

所以它与 `employees` 是**逻辑关系，不是外键关系**。

例如：

```
A：1000～2999
B：3000～5999
C：6000～9999
D：10000～14999
E：15000～24999
F：25000～40000
```

### 9. `order`：示例订单表

|列名|中文含义|说明|
|---|---|---|
|`order_id`|订单编号|该表中没有设置主键或唯一约束|
|`order_name`|订单名称|示例数据为 shkstart、tomcat、dubbo|

`order` 是 MySQL 的保留字，因此代码中通常写成反引号形式：`` `order` ``。这张表没有与员工、部门等表建立外键关系，基本是独立的演示表。

## 四、`emp_details_view` 视图

`emp_details_view` 不是实际存储数据的表，而是把员工及其组织信息组合后的查询结果。它包含：

|列名|中文含义|
|---|---|
|`employee_id`|员工编号|
|`job_id`|岗位代码|
|`manager_id`|直属上级编号|
|`department_id`|部门编号|
|`location_id`|办公地点编号|
|`country_id`|国家代码|
|`first_name`|名|
|`last_name`|姓|
|`salary`|工资|
|`commission_pct`|佣金比例|
|`department_name`|部门名称|
|`job_title`|岗位名称|
|`city`|城市|
|`state_province`|州或省|
|`country_name`|国家名称|
|`region_name`|地区名称|

它实际连接了：

```
employees
  → departments
  → jobs
  → locations
  → countries
  → regions
```

因此可以把它理解为“员工全景信息视图”。

## 五、实际查询时的主连接方式

查询员工完整信息时，通常按下面的链路连接：

```
SELECT
    e.employee_id,
    e.first_name,
    e.last_name,
    j.job_title,
    d.department_name,
    l.city,
    c.country_name,
    r.region_name
FROM employees e
JOIN jobs j
    ON e.job_id = j.job_id
LEFT JOIN departments d
    ON e.department_id = d.department_id
LEFT JOIN locations l
    ON d.location_id = l.location_id
LEFT JOIN countries c
    ON l.country_id = c.country_id
LEFT JOIN regions r
    ON c.region_id = r.region_id;
```

## 六、最容易混淆的几点

1. `employees.manager_id` 是员工的直属上级，`departments.manager_id` 是部门负责人。
2. `jobs.min_salary/max_salary` 是岗位薪资范围，`job_grades.lowest_sal/highest_sal` 是薪资级别范围。
3. `job_grades` 只能通过工资范围逻辑匹配员工，没有外键。
4. `job_history` 保存历史岗位和历史部门，当前信息在 `employees` 表中。
5. `order` 表没有主键、唯一键或外键，与其他表没有关系。
6. `departments` 和 `employees` 互相引用，属于循环关联；删除部门或员工时会受到外键约束影响。
