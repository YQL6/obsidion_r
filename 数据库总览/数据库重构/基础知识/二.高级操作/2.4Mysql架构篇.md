## 1.2卸载mysql

---

1. 关闭`mysql服务`
	- `systemctl stop mysql.service`
2. 删除对应应用，使用应用管理器
	- `sudo apt remove mysql`
	- 查看相关文件：
		- `find / -tepe d -name mysql`
		- `rm -rf ....` + `rm -rf /etc/my.cnf`

注：
1. `linux和ubuntu的指令细节不同`

## 1.3下载mysql

----

- 下载方式：
	- `yum`
	- `rpm格式使用rpm下载`
	- 使用压缩包获得

1. 官网下载:[官网](https://dev.mysql.com/downloads/mysql/)
2. 拉取到操作系统中，使用解压操作
   `tar ...`
3. 检查权限
	1. `mysql 要在 /temp中建立文件 ，赋予权限 ——》 chmod -R 777 /tmp`
	2. 依赖检查
4. 将解压的文件包/`.rpm`进行按一定顺序进行安装，指令必须指定对应的具体/相对路径
   `rpm -ivh ....`
5. 服务器初始化：
   `mysqld --initialize --user=mysql`
6. 查看密码:
   `cat /var/log/mysqld.log`
7. 启动服务:
   `systemctl start mysqld`
   `systemctl enable mysqld`
8. 登录`mysql`
   `mysql -uroot -p`
9. 更改密码：
   `alter user'root'@'localhost' identified by 'root';`

## 2.3SQL大小写规范

---

- 大小写是否敏感看`lower_case_table_names`
	- 体现的仅是数据库和表名是否敏感
	- 数据：
		- `0`:<mark style="background: #ABF7F7A6;">大小写敏感</mark>，`linux`
		- `1`:大小写不敏感，存储比较都是小写，windows
		- `2`:不敏感，比较都是小写，但是存储都是原样，mac
	- 其他：
		- sql语句大小写不敏感
		- 比较看`collaction`
		- 变量名：
			- <mark style="background: #FFF3A3A6;">除了局部变量都不敏感</mark>
	- 可以修改敏感，但是一般不修改——》难，麻烦

- `sql_mode`：
	- <mark style="background: #FFF3A3A6;">语法检查是否使用严格模式</mark>
	- 一般使用严格模式——》一般生成环境是严格模式
	- 默认配置：
	  `select @@session.sql_mode`
	- 可以修改对应的变量为`''`,默认变为宽松模式 / 手动修改配置文件
	  `set @@sql_mode = ''`

注：
1. `variables`<mark style="background: #ADCCFFA6;">即不是数据库又表示变量</mark>，是数据库的配置参数集合，可以通过sql查询找到里面内容，是各种参数，通过搜索引擎到配置文件读取数据，不会从数据库中读取数据

# 三.数据库执行流程

## 3.1Mysql架构

---

- 配置文件
	- 配置格式：
		- `ini格式`:
			- 键值对类型
			- `[xxx]`
				- 节标题，往往表示一个组，这个组有固定功能
				- 读取时不同的角色读取的节标题不同
					- 主程序
					- 客户端
					- 装包器
				- <mark style="background: #BBFABBA6;">不同命令执行读取不同标签组</mark>
			- 对于不同的版本可以设置对应的标签组，若是对应的版本启动，读取对应的标签组`[mysql-5.7]`
		- 配置的优先级：
			- 若是加载标签组，不同的标签组有相同的配置`key`相同，后声明的优先
			- 若是命令行指定一个变量是什么，则命令行优先级最高
	- <mark style="background: #FFB86CA6;">键值对`key`到数据库中就是变量</mark>
		- 变量:
			- <mark style="background: #FFB8EBA6;">系统变量/会话变量不能定义</mark>
			- 可以进行赋值——》临时起作用，<mark style="background: #FFF3A3A6;">到配置文件配置，可以永久修改</mark>

- 逻辑架构：
	- 总体架构：
		- <mark style="background: #BBFABBA6;">经典的`C/S`架构，服务器端使用的程序是`mysqld`</mark>
		- `c/s`间无论如何通信，最终实现的效果相同：
		  ![[Excalidraw/数据库总览/数据库重构/基础知识/二.高级操作/2.4Mysql架构/三.数据库执行流程/3.1Mysql架构/服务器的处理流程|服务器的处理流程]]
			- 客户端进程想服务器进程发送文本/`sql`,服务器端处理后想客户端返回一段文本/处理结果
		- 经典的老架构：
		  ![[Excalidraw/数据库总览/数据库重构/基础知识/二.高级操作/2.4Mysql架构/三.数据库执行流程/3.1Mysql架构/架构经典|架构经典]]
			- `5.7`:
				- 有缓存机制
			- `8.0`:
				- 没有缓存机制了
			- 详细结构:
				- `Connetors/客户端`:
					- 通过各种连接工具连接服务端
				- 连接层：
					- 连接池/多线程提供服务 ——》 <mark style="background: #FF5582A6;">处理连接</mark>，验证权限/密码账号/权限表
				- 服务层/`service`:
					- <mark style="background: #FFF3A3A6;">接口，解析，优化，缓存</mark>
					- 获得sql命令，返回sql结果
					- 解析(发现报错问题)
					- 对sql优化:生成一个执行计划，不一定生成执行时间最短的
					- 查询结果先放到缓存中，然后放到sql接口返回(8.0删掉了)
						- `5.7`:
							- `SHOW VARIABLES LIKE 'query_cache%'`
								- 数值：
									- `0`:不适用缓存
									- `1`:使用缓存
									- `2`:按需使用缓存，具体指定首付
					- 执行器(被包裹在接口中)：
						- 获得计划执行，调用引擎
				- `引擎层`:
					- 引擎
						- 负责真正的查询
				- 存储层：
					- `select variables like '%datadir%'`

- 客户端的连接池 VS 连接层的连接池：
	- 客户端：
		- 面对的是`TCP`对象，会对连接管理，进行复用
	- 连接层:
		- 面对的是线程，会对会话资源和线程进行管理，复用线程，避免多次销毁和建立

## 3.2SQL执行流程

---

1. 查询缓存：
	- 命中(很低)：发现这条sql命令(<mark style="background: #ABF7F7A6;">必须完全一样/很难出现,即使是空格也不可以</mark>)直接返回
		- 可能发生错误：
			- `now`
			- 删除后的命令
		- 变量名:
			- `query_cache_type`:
				- 0,1,2
	- 没命中：向下走
2. 解析器：
	- 大体流程：
	  ![[图片/Pasted image 20261014142328.png]]
	- 生成对应的解析树：<mark style="background: #FFB86CA6;">根据关键字解析(对应操作的关键字和操作对象)和语法解析(看看对不对)</mark>
	  ![[图片/Pasted image 20261014141803.png]]
	- 解析树进行<mark style="background: #D2B3FFA6;">预处理生成一个新的解析树</mark>
	- <mark style="background: #FFF3A3A6;">解析之后进行权限检查</mark>
3. 优化器
	- <mark style="background: #ABF7F7A6;">生成执行计划</mark>——》选择时间最少和成本最低的方案
		- 全表检索/索引检索等做为依据
	- 优化方式：
		- 逻辑查询优化：
			- 语法上
		- 物理查询优化、
			- 索引，表的连接方式
4. 执行器：
	- 调用具体的存储引擎`API`
5. 存储引擎
	- 通过API接口查询数据
	- 结果返回缓存，同时将结果返回给SQL接口
		- 全表查询：
			- 对表格进行逐行查询若是符合条件，放到结果集

## 3.5数据库缓冲池

----

- `Innodb`引擎到磁盘对磁盘操作：
	- 加载到内存中：
		- 引擎按页对数据库磁盘进行管理，<mark style="background: #FFF3A3A6;">将数据加载到内存中进行操作</mark>
	- 缓存：
		- 将加载到内存的数据，<mark style="background: #FFF3A3A6;">保留在内存中，不必多次访问磁盘</mark>，避免速度`IO过多`
		- 保存位置：
			- 缓冲池：
				- 保存数据页的具体数值，索引，锁等信息

- <mark style="background: #ABF7F7A6;">所有优化操作的基础都是针对内存上的数据</mark>

- 缓存的原则：
	- <mark style="background: #FFB86CA6;">位置 + 频次</mark>：
		- 位置：
			- 首先位置在内存中才能对其优化，缓存放到内存中
		- 频次：
			- <mark style="background: #FFF3A3A6;">频次决定优先级顺序</mark>，<mark style="background: #FFB86CA6;">优先加载频次高的热数据到内存中</mark>
	- 预缓存：
		- 当使用一些数据时，<mark style="background: #ABF7F7A6;">大概率会使用前后附近的数据</mark>，加载时一起加载前后的数据页 ——》空间局部性原理

- 缓冲池 VS 缓存
	- 缓存
		- `缓存保存的是查过的数据:sql语句`
	- 缓存池：
		- <mark style="background: #ABF7F7A6;">将内存中保留磁盘中可能查询的数据 ——》 必有</mark>

- 缓冲池交互行为：
  ![[Excalidraw/数据库总览/数据库重构/基础知识/二.高级操作/2.4Mysql架构/三.数据库执行流程/3.5数据库缓冲池/缓冲池|缓冲池]]
	- 修改数据：
		- 先给内存数据 
		- 内存刷到磁盘中 ——》 永久保存
			- 非实时刷新
				- 一定策略，例如：一定频率

- 缓存池操作：
	- `MyISAM`:
		- <mark style="background: #D2B3FFA6;">只缓冲索引，不缓存数据 ——》交给内核管理</mark>
		- `key_buffer_size`变量表示
		- 本质上就不是缓冲池
	- `InnoDB`:
		- 缓冲数据和索引等信息
		- `innodb_buffer_pool_size`表示大小
		  ![[图片/Pasted image 20261014180729.png]]
			- 缓冲池的大小，可以修改

- 多实例：
	- 缓冲池可以多个实例，避免锁问题，这是为了避免锁一整个或大范围的缓冲池对吗，不是为了一个表被多个查询
	- 锁问题：
		- 一个大锁将整个缓冲池锁住，为了避免这个问题 ——》 将缓冲池拆为多个
		- 多个实例
	- 内存分配问题：
		- `innodb_buffer_pool_size表示总量大小，又几个实例平分`
		- 若是缓冲池总内存小于`1GB`，无意义，不会为你创建

- 更新规则：
	- 查询操作：
		- 若是缓冲中没有，从磁盘中获取，加载到缓冲池中然后进行查询
	- 更新操作：
		- 若是缓冲池中没有，从磁盘获得，加载到缓冲池中进行更新操作——》在内存中，磁盘中没有
		- <mark style="background: #BBFABBA6;">定期将更新</mark>的数据刷到磁盘中 ——》 还<mark style="background: #FFB86CA6;">没有刷的内容</mark> ——》 <mark style="background: #BBFABBA6;">脏数据/脏页</mark>
		- 事务问题：
			- <mark style="background: #BBFABBA6;">刷新过程中若是刷新到一半，刷新的数据进行回滚</mark>

## 4.2InnDB VS MyISAM

---

- `5.5以后默认使用`

- `InnoDB`:
	- 功能特征：
		- 具备<mark style="background: #FFB86CA6;">支持外键支持功能</mark>的事务存储引擎的事务存储引擎
			- 外键一般不使用，会导致数据间修改受限
		- <mark style="background: #BBFABBA6;">支持事务</mark>
			- 重要 —— 》 所以优先考虑`InnoDB`
			- 例如：
				- 刷新到磁盘中，若是突然中断，<mark style="background: #ABF7F7A6;">重启以后无需额外操作来统一数据，事务已经回滚</mark>
		- <mark style="background: #FFF3A3A6;">支持行锁，一个操作锁一行</mark>
	- <mark style="background: #ABF7F7A6;">若是想要更新，删除等修改数据的操作，建议使用`Innodb`</mark>
	- 推荐使用，擅长处理大数据量
	- 缺点：
		- 处理效率低
		- 内存要求低 ——》 要加载索引 + 数据
- `MyISAM`:
	- 功能特征：
		- 不支持事务和外键
		- 支持表锁，一个操作锁一个表
		- 针对数据统计又额外存储 ——》 `count(*)`达到`O(1)
	- 若是仅查询数据的操作，建议使用`MyISAM`
	- 缺点：
		- 崩溃后无法恢复 ——》不支持事务

| 维度 | InnoDB | MyISAM | 差异性质 |
| --- | --- | --- | --- |
| 事务 / ACID | 完整支持，MVCC，四种隔离级别 | 不支持，语句失败无法回滚 | 根本差异 |
| 锁粒度 | 行级锁（含间隙锁、意向锁） | 表级锁，一次写入阻塞整表 | 根本差异 |
| 索引结构 | 聚簇索引，主键叶子即完整行 | 非聚簇，叶子存行物理偏移 | 根本差异 |
| 数据缓存 | Buffer Pool 统一缓存索引页 + 数据页 | key cache 只缓存索引，数据交给 OS page cache | 根本差异 |
| 崩溃恢复 | redo + undo 自动恢复 | 无日志，需 REPAIR，可能丢数据 | 根本差异 |
| 内存可控性 | 命中率可观测、可预热、淘汰策略可调 | 数据页无指标，只能调内核参数 | 根本差异 |
| 磁盘占用 | 偏大（页预留、undo、旧版本） | 紧凑，myisampack 可压至 40–70% | InnoDB 劣势 |
| 并发写入 | 读写不互相阻塞，适合高并发 | 写串行化，适合读多写极少 | InnoDB 优势 |
| COUNT(*) 无 WHERE | 需扫描，选最小二级索引 | O(1)，直接读表头计数 | MyISAM 优势 |
| 全表扫描 | 聚簇索引叶子跳页，物理不连续 | 堆表顺序读，预读跑满带宽 | MyISAM 优势 |
| 外键约束 | 支持 | 语法可写但被忽略 | 根本差异 |
| 全文索引 | 5.6 起支持 | 原生支持 | 已拉平 |
| 空间索引 | 5.7 起支持（R-tree） | 支持（R-tree） | 已拉平 |
| 自增主键持久化 | 8.0 起持久化，重启不回退 | 存于 .MYI 头部，一直持久 | 已拉平 |
| 物理文件 | .ibd + ib_logfile*（不能直接拷） | .MYD + .MYI（停机直接拷） | 运维差异 |
| 热备份 | xtrabackup 在线备份 | 无在线方案，需锁表或停机 | InnoDB 优势 |
| 崩溃后数据安全 | 已提交事务不丢 | 表可能损坏、数据可能丢 | 根本差异 |
