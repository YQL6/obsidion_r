# 一.日志

## 1.1六大日志

---

- 日志总览：
	- 通用查询日志：
		- 记录从连接开始的起始时间，终止时间，以及发售给你给连接的数据库的所有指令
		- 可以通过通用查询日志来重现所有操作，场景 ——》 发现问题，审计
		- 要不断保存，清空这个日志
	- 慢查询日志：
		- 记录被视为慢查询的<mark style="background: #BBFABBA6;">`sql语句`</mark>
	- 错误日志：
		- 数据库从开始到系统终止时出现的问题，例如：死循环导致内存终止
	- 二进制日志：
		- 记录所有更改数据的语句
		- 不可以使用记事本直接打开看，二进制格式
		- 格式：
			- `sql`语句
			- 具体什么行发生变化
		- 作用:
			- 主从服务器间同步问题，读服务器来读这个日志
			- 故障数据恢复
	- 中继日志：
		- 读服务器读二进制日志，读到中继日志中，等待数据库系统来读取这个日志同步写操作
	- 数据定义日志：
		- 记录数据定义语句执行的元数据操作
		- 保证`DDL`操作的原子性

- 除了二进制日志都是文本文件，建于`mysql数据目录`中

- 日志缺点：
	- 存储空间占用
	- 降低`mysql`的效率，操作的同时还要对日志进行写入操作

## 1.2通用查询日志，错误日志

----

- 通用查询日志：
	- 查看通用查询日志，还原操作时的具体场景 ——》 到底发送了什么导致的问题
	- 场景：
		- 用户付款第一次使用微信付款未成功，进行第二次使用字符表支付，通过回看通用查询日志，发现当时网络故障，微信支付的回调未收到，到晚上才收到，但是已有支付宝的付款记录，覆盖
	- 变量：
		- `general_log`:
			- 是否开启，默认关闭
		- `general_log_file`:
			- 通用查询日志记录的存储位置
	- 删除，刷新日志：
		- 将原来的日志进行更改名字，`mysql`在对日志写入，发现日志没有了进行创建
		- 删除备份
		- 更改路径
	- 刷新日志:
		- `mysqladmin -uroot -proot -flush -logs`

- 错误日志：
	- 从服务器启动和停止时的时间，以及过程中的诊断信息，例如：错误，警告，提示等
	- 错误先从这里面找
	- 变量：
		- `log-error`:
			- 文件位置
			- 默认:
				- `linuex`:
					- `mysqld.log`
				- `mac`:
					- `hostname.error`
	- 删除，刷新日志:
		- 更名
		- 删除备份
		- 更改路径
	- 刷新日志：
		- `mysqladmin -uroot -proot -flush -logs`

注：
1. 在刷新前要执行一下`install -omysql -gmysql -m0644 /dev/null /var/log/mysqld.1og`,因为这个可以为数据库创建一个正确的文件
2. 一定要在文件备份，创建以后刷新一下，使数据库获得新文件**“文件句柄（File Descriptor / inode）”**

## 1.3二进制日志

---

- `binlog`:
	- 变更日志：只记录<mark style="background: #FFF3A3A6;">数据变化</mark>的语句
		- `DDL`语句
		- `DMl`语句
	- 作用：
		- 数据恢复：
			- 数据库奔溃以后，根据提交最后的数据的保存时间点读取二进制日志内容恢复数据
		- 数据复制：
			- 读服务器通过读取整个日志，同步写操作到读服务器
		- 数据备份：
			- 主主，主从
	- 二进制日志形式保存，不能直接读，保存形式是以事件形式，<mark style="background: #FFB86CA6;">事件提交是写入的唯一触发点</mark>
	- 变量:
		- `log_bin`:
			- 是否开启
		- `sql_log_bin`:
			- 变更行为是否记录到日志中，默认开启
			- 只能对会话级别的变量进行变更，全局级别的被设置为只读的了
		- `log_bin_basename`:
			- 日志位置
		- `log_bin_index`:
			- 表示不会只有一个二进制文件，有多个，不同的使用索引来表示不同
			- 每次启动都创建一个二进制文件
		- `log_bin_trust_function_creators`:
			- 是否允许创建函数，可能发生不安全的函数或者无法主从复制的函数
			- 不影响使用已有的函数
	- 设置永久生效参数：
		- `log-bin`:
			- 日志文件名
		- `binlog_expire_logs_seconds=xxx`:
			- 日志保存时间
			- 从最后一次写入开始算
		- `max_binlog_size`:
			- 日志文件大小
			- 默认`1GB`，若是超过自动生成一个写入，最大`1GB`
			- 大小设置其实不是很严格，若是一个事务很大，写入超过`1GB`也会存储在里面，不会另起一个写入
	- <mark style="background: #ABF7F7A6;">数据库文件和二进制日志文件最好不要放到一起</mark>，避免一起损坏
	- 移动文件：
		- 停止 MySQL 服务：这是必须的，以确保数据一致性。
		- 修改配置文件：在 my.cnf 或 my.ini 中，修改 log-bin 和 log_bin_index 指向新的绝对路径。
		- 移动或复制文件：将旧的 Binlog 文件（mysql-bin.*）和索引文件（.index）移动到新目录。
		- 处理索引文件（关键）：如果 .index 文件里记录的是绝对路径，必须手动编辑它，将所有路径更新为新位置。
		- 检查权限：确保 MySQL 用户对新的目录和文件有读写权限。
		- 启动 MySQL 服务：重启后，MySQL 就会使用新的路径记录 Binlog。

- 查看文件信息：
	- `mysql内部`:
		- `show binary logs`:
		  ![[图片/Pasted image 20261024124538.png|444]]
			- 查看二进制日志所有的文件的信息
		-  `show binlog events [in logsname] [from pos] [limit index|offset]`只能看到骨架信息，无法看到具体的变更数据
		  ![[图片/Pasted image 20261024132125.png]]
			- `logsname`:
				- 要查看的二进制文件的名字
			- `from pos`:
				- 从哪个点开始读
			- `limit index|offset`
				- 分页读取
	- `mysql外部`:
		- `mysqlbinlog -v 文件路径`
			- 通过文件查看，将文件内容以伪`sql`展示 ——》 以事务形式来展示,一个事务多个事件
				- `query`
				- `table_map`
				- `Write_rows`
				- `XID`
			- 使用的是`mysqlbinlog`工具来转换的
		- `mysqlbinlog工具使用`:
			- `mysqlbinlog --no-defaults --help`:
				- 查看工具的帮助信息
	- `binlog的存储格式`:
		- 格式
			- `Statement`:
				- 记录每一条修改数据的`sql语句`
				- 无需对每一行的变化进行记录，减少了`binlog`日志量
			- `ROW`
				- 记录了那条记录被修改，修改为了什么，仅是表的什么部位修改为什么，不是物理上的位置
				- <mark style="background: #ABF7F7A6;">精确的记录了每一行数据修改的细节</mark>，避免了特殊情况下的存储过程/函数/触发器调用和触发无法正确同步到读服务器中
			- `Mixed`
				- `Statement和ROW`的结合
		- 查看:
			- `show variables like 'binlog_format';`

- 数据恢复：
	- `flush logs`:
		- 刷新文件，对于二进制日志文件进行开启一个新的文件记录，避免记录恢复操作
	- `show binlog events in logs from pos limit index|offset':
		- 根据`pos`查看具体内容
		- 若是想要以时间戳解决，使用`mysqlbinlog`
	- 使用`mysqlbinlog`进行恢复数据
		- 查手册
